# java常用命令

## jstat

### `jstat -gc <pid> <间隔ms>`

`jstat -gc <pid> <间隔ms>` 是监控 JVM 堆内存和 GC 状态的核心命令，每一列对应内存区域 / GC 统计指标

各列含义如下：

| 列名 | 全称                            | 含义                                                                       |
| ---- | ------------------------------- | -------------------------------------------------------------------------- |
| S0C  | Survivor 0 Capacity             | 新生代「幸存区0」的**总容量**（当前分配的大小）                            |
| S1C  | Survivor 1 Capacity             | 新生代「幸存区1」的**总容量**                                              |
| S0U  | Survivor 0 Used                 | 幸存区0的**已使用大小**                                                    |
| S1U  | Survivor 1 Used                 | 幸存区1的**已使用大小**                                                    |
| EC   | Eden Capacity                   | 新生代「伊甸园区」的**总容量**（新生代核心区域，对象优先分配到这里）       |
| EU   | Eden Used                       | 伊甸园区的**已使用大小**                                                   |
| OC   | Old Capacity                    | 老年代的**总容量**（存放存活时间长的对象）                                 |
| OU   | Old Used                        | 老年代的**已使用大小**                                                     |
| MC   | Metaspace Capacity              | 元空间（Metaspace）的**总容量**（存储类信息、方法元数据，JDK8 替代永久代） |
| MU   | Metaspace Used                  | 元空间的**已使用大小**                                                     |
| CCSC | Compressed Class Space Capacity | 压缩类空间的总容量（元空间的细分，存储类的压缩指针信息）                   |
| CCSU | Compressed Class Space Used     | 压缩类空间的已使用大小                                                     |
| YGC  | Young GC Count                  | 新生代 GC（YGC，又称 Minor GC）的**总次数**                                |
| YGCT | Young GC Time                   | 新生代 GC 的**总耗时（秒）**                                               |
| FGC  | Full GC Count                   | Full GC 的**总次数**（整堆回收，耗时久，应尽量避免）                       |
| FGCT | Full GC Time                    | Full GC 的**总耗时（秒）**                                                 |
| CGC  | Concurrent GC Count             | 并发 GC 次数（G1GC 特有，如并发标记、并发清理）                            |
| CGCT | Concurrent GC Time              | 并发 GC 总耗时（秒）                                                       |
| GCT  | Total GC Time                   | 所有 GC 的**总耗时（秒）**                                                 |

输出示例：

```shell
/ # jstat -gc 1 1000
S0C         S1C         S0U         S1U          EC           EU           OC           OU          MC         MU       CCSC      CCSU     YGC     YGCT     FGC    FGCT     CGC    CGCT       GCT   
0.0     29696.0         0.0     29696.0     307200.0     274432.0     627712.0     566141.0   222848.0   220615.3   22336.0   21113.1    214     6.156     0     0.000    78     0.747     6.903
0.0     17408.0         0.0     17408.0     315392.0          0.0     631808.0     581006.3   223488.0   221283.3   22336.0   21140.7    215     6.189     0     0.000    78     0.747     6.936
```

## 未整理的ai内容

### 从输出中能看出的关键信息

#### 1. 堆内存风险：老年代接近满负荷（最高优先级）

- 老年代已用 90%（540MB/600MB），且在监控周期内**没有下降**——说明对象从新生代晋升到老年代的速度，远快于 G1 并发回收老年代的速度；
- 若老年代持续占满，G1 会触发「混合回收」（Mixed GC）甚至 Full GC（虽然目前 FGC=0，但已接近临界值），Full GC 会导致应用停顿（STW），影响可用性。

#### 2. 新生代状态：即将触发 YGC

- 伊甸园区已用 87% + 幸存区1 100%，新生代剩余可用内存极少（≈300-260 + 28.4-28.4 = 40MB）；
- 按照这个内存增长速度，**几秒内就会触发下一次 YGC**（新生代满了就会触发 YGC）；
- 你的 YGC 累计 215 次，单次耗时≈29ms（6.189秒/215次），这个单次耗时是合理的（YGC 单次应控制在 50ms 内），但频率若过高（比如每分钟多次），累计耗时会影响性能。

#### 3. 元空间接近耗尽（次高优先级）

- 元空间已用 99%（210MB/212.5MB），元空间默认「无上限」（受容器总内存限制），但当前已接近分配的上限；
- 元空间不足会触发「元空间扩容」（JVM 自动申请），频繁扩容会增加 GC 压力，甚至触发 Full GC（元空间扩容失败时）；
- 元空间高占用通常是因为：加载的类太多（比如动态代理、热部署、依赖包过多）、类卸载失败（内存泄漏）。

#### 4. 积极信号：无 Full GC

- FGC=0 说明当前 G1GC 的并发回收机制还能扛住，没有触发最耗时的整堆回收，这是好现象——但需立即优化，否则很快会出现 FGC。

#### 5. G1 并发回收效率：基本正常

- CGC=78 次（并发 GC 次数），CGCT=0.747 秒（总耗时），单次并发 GC 耗时≈9.6ms——并发 GC 是「非停顿」（或低停顿）的，这个耗时对应用无明显影响。

### 三、针对性优化建议（按优先级排序）

#### 1. 紧急：缓解老年代高占用

- **短期**：适当调大堆内存上限（若容器内存有富余）——比如把 `MaxRAMPercentage` 从 85% 调到 90%（前提是容器总内存≥6GB，预留至少 5% 给系统/非堆），让老年代有更多缓冲空间；
- **长期**：分析内存泄漏/大对象——用 `jmap -dump:format=b,file=heap.hprof 1` 导出堆快照，用 MAT/JProfiler 分析：
  - 哪些对象占用老年代最多（比如大集合、未关闭的连接、静态变量引用）；
  - 是否有对象「应该被回收但一直存活」（内存泄漏）。

#### 2. 优化元空间占用

- 临时扩容：添加 JVM 参数 `-XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m`（初始256MB，最大512MB），避免频繁扩容；
- 根因排查：
  - 检查应用是否有「类加载泄漏」（比如自定义类加载器未释放）；
  - 减少不必要的依赖包（比如冗余的 jar 包会加载更多类）；
  - 若用 Spring Boot，关闭不必要的自动配置、减少动态代理（比如 AOP 过度使用）。

#### 3. 优化 G1GC 新生代策略

- 调大新生代初始比例：添加 `-XX:G1NewSizePercent=30 -XX:G1MaxNewSizePercent=50`（新生代占堆的初始30%、最大50%）——当前新生代仅 300+28=328MB（占堆 600MB 的 55%，但老年代只有 600MB），调大新生代能减少对象过早晋升到老年代；
- 触发混合回收阈值：添加 `-XX:G1MixedGCLiveThresholdPercent=85`（老年代区域存活对象占比低于85%时触发混合回收，默认85%，可略调低到80%，让G1更早回收老年代）。

#### 4. 监控补充

- 持续监控 `jstat -gcutil 1 1000`（百分比视图，更直观）：关注 `O`（老年代使用率）、`YGC` 增长频率；
- 监控容器内存：`docker stats`/`kubectl top pod`，确认容器总内存是否有富余（避免JVM堆调大后容器OOM）。

### 四、总结

你的 JVM 配置（RAMPercentage）虽然生效，但**内存使用已接近临界值**：老年代 90%、元空间 99%、新生代即将触发 YGC，核心风险是「老年代占满导致 Full GC」。

优先做 2 件事：

1. 临时扩容堆内存/元空间，避免短期出现 Full GC；
2. 导出堆快照分析内存泄漏/大对象（这是根本问题）。

当前无 Full GC 是关键缓冲期，抓紧优化即可避免应用卡顿。

# Java服务jstat日志分析与OOM排查报告

## 一、日志关键指标说明

在分析jstat日志前，先明确核心指标含义（单位：KB，时间单位：秒），后续重点分析均围绕这些指标展开：

| 指标 | 含义 | 关键关注点 |
|------|------|------------|
| S0C/S1C |  Survivor 0/1区总容量 | 稳定不变，反映JVM初始配置 |
| S0U/S1U | Survivor 0/1区已使用容量 | 若长期接近S0C/S1C，可能存在内存无法回收问题 |
| EC/EU | Eden区总容量/已使用容量 | EU持续增长且无法快速下降，是OOM核心预警信号 |
| OC/OU | 老年代总容量/已使用容量 | OU接近OC时，老年代内存耗尽，直接触发OOM |
| MC/MU | 元空间总容量/已使用容量 | MU持续增长可能导致元空间OOM（非本次案例主因） |
| YGC/YGCT | 年轻代GC次数/总耗时 | 次数骤增、耗时变长，说明年轻代内存压力大 |
| FGC/FGCT | Full GC次数/总耗时 | FGC突增且耗时飙升，是OOM前的关键异常 |
| GCT | GC总耗时 | 占业务时间比例过高，会导致服务卡顿甚至OOM |

## 二、重点关注行提取（按时间顺序，突出异常变化）

### 1. 初始稳定阶段（前13行）

- **关键数据**：EC=313344KB，EU从228352KB逐步增长至292864KB；YGC=249，YGCT=9.591；FGC=0，FGCT=0。
- **状态分析**：Eden区使用量稳步上升，年轻代GC正常（无Full GC），内存回收机制暂未异常。

### 2. 第一次内存波动（第14行）

- **关键数据**：EU从292864KB骤降至8192KB；MC从225088KB增至226304KB；YGC从249增至250，YGCT从9.591增至9.630。
- **异常点**：Eden区骤降是年轻代GC触发的正常回收，但元空间（MC）首次增长，需关注后续是否持续扩容。

### 3. 内存配置调整阶段（第23-24行）

- **异常点**：JVM内存区域（Survivor、Eden、老年代）容量首次调整，元空间回收（CGC）次数和耗时增加，说明内存压力开始传导至老年代和元空间。

### 4. 老年代压力显现阶段（第42行后）

- **关键数据**：OU从522795.9KB逐步增长至538164.3KB（OC=580608KB，使用率超92%）；YGC=253，YGCT=9.787；FGC仍为0，但CGCT稳定在2.083。
- **异常点**：老年代已使用量接近总容量，年轻代GC无法将内存回收至 Survivor 区，大量对象直接进入老年代，为后续OOM埋下隐患。

### 5. OOM前临界阶段（最后20行）

- **关键数据**：
  - EC/EU：EC从332800KB骤降至0-4096KB，EU长期维持低水平（说明年轻代对象快速进入老年代）。
  - OC/OU：OC从584704KB骤增至1536000KB（JVM尝试扩容老年代），但OU同步增至1535003.7KB（使用率超99.9%）。
  - FGC/FGCT：FGC从0暴增至107次，FGCT从0飙升至306.677秒（Full GC频繁触发且耗时极长，完全无法回收老年代内存）。
  - YGC/YGCT：YGC从257增至339，YGCT从9.915增至14.000（年轻代GC效率下降，频繁触发但回收效果差）。
- **致命异常**：老年代容量扩容后仍被占满，Full GC完全失效，内存无法释放，最终触发OOM。

## 三、OOM原因定位

结合日志分析，本次OOM的核心原因是**老年代内存泄漏+内存回收机制失效**，具体拆解为以下3点：

### 1. 大量对象无法被年轻代GC回收，直接进入老年代

- 日志中Eden区（EU）多次骤降后快速回升，说明年轻代对象创建速度远大于回收速度，且部分对象生命周期过长（超过15次年轻代GC仍存活），按JVM规则直接晋升老年代，导致老年代（OU）持续增长。

### 2. 老年代内存泄漏，Full GC无法回收

- 老年代使用率从初始的91.3%（522795.9/572416）逐步升至99.9%（1535003.7/1536000），且Full GC次数从0暴增至107次，FGCT达306.677秒，说明老年代存在大量**不可回收对象**（如静态集合未清理、线程池未关闭导致的对象引用残留、第三方组件内存泄漏等），Full GC无法释放内存，最终耗尽老年代空间。

### 3. 内存配置不合理，加剧OOM风险

- 初始Survivor区（S0C=0，S1C=19456KB）配置失衡，S0区长期闲置，导致年轻代对象无法在 Survivor 区充分存活和筛选，过早进入老年代；
- 元空间（MC）多次扩容（从225088KB增至232128KB），虽非本次OOM主因，但元空间持续增长可能占用系统内存，间接压缩老年代可使用空间。

## 四、OOM排查步骤（按优先级排序）

### 1. 紧急恢复：获取内存快照，定位泄漏对象（最关键）

- **操作命令**：在服务未完全宕机前，通过`jmap`工具生成堆内存快照（需提前安装JDK，确保`jmap`可用）：

  ```bash
  # 1. 查看Java进程ID（替换为你的服务名称，如java -jar xxx.jar）
  jps -l | grep 服务关键词
  # 2. 生成堆快照（pid为上一步获取的进程ID，dump.hprof为快照文件名）
  jmap -dump:format=b,file=dump.hprof [pid]
  ```

- **分析工具**：
  - 使用JDK自带的`jhat`工具（轻量）：`jhat dump.hprof`，通过浏览器访问`http://localhost:7000`查看对象分布；
  - 使用专业工具（推荐）：Eclipse MAT（Memory Analyzer Tool，需下载安装），导入快照后执行“Leak Suspects”分析，直接定位内存泄漏的对象类型和引用链（如`HashMap`静态集合未清理、`ThreadLocal`未移除导致的对象堆积）。

### 2. 检查Full GC日志，确认回收细节

- **操作步骤**：
  1. 查看JVM启动参数，确认是否开启Full GC日志（若未开启，需后续添加）：

     ```bash
     # 查看JVM参数（pid为进程ID）
     jinfo -flags [pid]
     ```

  2. 若已开启，找到日志文件（通常路径在启动参数`-Xloggc:/path/to/gc.log`中），重点关注：
     - 每次Full GC前后的老年代使用量（如`Before GC: Old Gen [538164K->538164K(580608K)]`，表示回收后无内存释放，确认内存泄漏）；
     - Full GC的原因（如`Allocation Failure`表示年轻代对象无法分配，被迫触发Full GC，进一步验证老年代已满）。
  3. 若未开启，后续需在JVM启动参数中添加（避免下次OOM无日志可查）：

     ```bash
     -Xloggc:/var/log/java/gc.log -XX:+PrintGCDetails -XX:+PrintGCTimeStamps -XX:+PrintHeapAtGC
     ```

### 3. 分析业务代码，定位泄漏场景

结合内存快照定位的泄漏对象，重点排查以下代码场景：

- **静态集合未清理**：如`static HashMap<String, Object> cache = new HashMap<>();`，长期put对象但未remove，导致对象永久驻留老年代；
- **线程池/线程泄漏**：如创建线程后未关闭，线程持有业务对象引用（如`ThreadLocal`未调用`remove()`），导致对象无法回收；
- **第三方组件泄漏**：如数据库连接池未配置最大连接数、Redis客户端未释放连接，导致连接对象堆积；
- **大对象创建**：如一次性读取大文件、生成大JSON字符串，对象超过Eden区容量，直接进入老年代且无法回收。

### 4. 优化JVM内存配置，缓解短期压力

在定位并修复代码问题前，可临时调整JVM配置缓解内存压力（需重启服务）：

- **调整年轻代与老年代比例**：默认老年代占堆内存2/3，可根据业务对象生命周期调整（如年轻代对象多则增大年轻代）：

  ```bash
  # 堆内存总容量设为4G，年轻代（-Xmn）设为2G，老年代则为2G
  -Xms4G -Xmx4G -Xmn2G
  ```

- **优化Survivor区比例**：通过`-XX:SurvivorRatio`调整Eden与Survivor比例（默认8:1，可改为4:1，让Survivor区容纳更多短期对象）：

  ```bash
  -XX:SurvivorRatio=4
  ```

- **开启老年代扩容阈值调整**：避免老年代过早满溢，通过`-XX:CMSInitiatingOccupancyFraction`（CMS收集器）或`-XX:InitiatingHeapOccupancyPercent`（G1收集器）设置老年代触发Full GC的阈值（如70%，即老年代使用率达70%时触发Full GC）：

  ```bash
  # CMS收集器示例（适合老年代对象多的场景）
  -XX:+UseConcMarkSweepGC -XX:CMSInitiatingOccupancyFraction=70 -XX:+UseCMSInitiatingOccupancyOnly
  ```

### 5. 长期监控：搭建内存监控体系

为避免后续OOM无法提前预警，需搭建实时监控：

- **工具选择**：Prometheus + Grafana（开源）、JVisualVM（本地调试）、Arthas（阿里开源，在线排查）；
- **监控指标**：老年代使用率（阈值设85%报警）、Full GC次数（每分钟超5次报警）、年轻代GC耗时（单次超100ms报警）；
- **报警触发**：当指标超过阈值时，通过邮件/钉钉推送报警，及时介入处理。

## 五、总结

本次OOM的核心是**老年代内存泄漏**，而非单纯的内存配置不足。短期需通过`jmap`获取快照定位泄漏对象，中期优化JVM配置缓解压力，长期需修复代码泄漏点并搭建监控体系。排查时优先从“内存快照+Full GC日志”入手，可快速定位90%以上的OOM原因。
